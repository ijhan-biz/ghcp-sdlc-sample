GitHub-native SDLC GHAS 5-layer DDD + BDD Go / No-Go

0) 데모 시작 링크

아래 링크를 순서대로 열어두면 발표 중 전환이 빠릅니다.

Seed SDLC Workflow SDLC Issues Demo PR List Dependency Review Workflow Dependency Review Example Run Security Overview

완료 기준: 탭 6개를 미리 열고 발표 순서대로 좌우 이동만 하면 됩니다.

1) 10분 스크립트 (핵심)

  1. Actions · 0:00~2:00 seed 실행 결과를 열고 8단계 이슈 자동 생성 흐름을 보여준다.
    "클릭: Actions -> seed-sdlc-demo -> 최신 successful run. 확인: workflow_dispatch로 실행됐고, Stage 이슈 생성이 완료됐는지 로그를 봅니다. 멘트: 개발 작업은 채팅으로 끝나지 않고 GitHub 증거로 남습니다. 오늘은 SDLC 8단계가 이슈로 자동 생성되는 운영 흐름을 보여드립니다."
  2. Issues · 2:00~4:00 `label:sdlc-stage` 목록에서 Plan과 Govern 이슈를 1개씩 연다.
    "클릭: Issues -> label:sdlc-stage -> [PLAN] 이슈 오픈 -> [GOVERN] 이슈 오픈. 확인: Leader question, Stop condition, Evidence link 3개 섹션이 있는지 확인합니다. 멘트: AI에 맡기기 전에 리더가 승인해야 할 질문과 멈춤 기준을 먼저 합의합니다. 이게 없으면 다음 단계로 넘기지 않습니다."
  3. PR · 4:00~6:30 데모 PR 목록에서 open PR 하나를 열어 required checks를 보여준다.
    "클릭: Pull Requests -> sdlc-demo 라벨 PR 1건 오픈. 확인: PR 본문의 Why/What/Demo point, CODEOWNERS 리뷰, required checks 상태를 확인합니다. 멘트: AI PR은 완성이 아니라 리뷰 요청입니다. 승인 경계는 사람 리뷰와 체크 결과입니다."
  4. GHAS · 6:30~10:00 Dependency Review workflow와 example run을 연다.
    "클릭: Actions -> dependency-review workflow -> example run 오픈. 확인: workflow_dispatch 수동 실행 기록, Manual demo summary, PR 이벤트 시 게이트 동작 설명을 확인합니다. 멘트: 실패 로그는 우회 대상이 아니라 다음 입력입니다. 보안 게이트는 배포 뒤가 아니라 PR 앞단에서 작동합니다."

2) 15분 스크립트 (권장)

  1. 확장 1 · 10:00~11:00 10분 스크립트 전체를 먼저 실행한다.
  2. 확장 2 · 11:00~13:00 Security 탭에서 Overview를 열고 `SECURITY.md` 정책 링크로 이동한다.
    "클릭: Security -> Overview -> Security policy. 확인: 코드/시크릿/의존성 관련 보안 상태를 한 화면에서 보여주고, 정책 문서로 이동합니다. 멘트: GHAS는 개발자 편의 기능이 아니라 운영 통제 체계입니다. Code scanning(CodeQL)은 push/PR 시점 분석, Secret scanning은 커밋/푸시 및 전수 스캔, Dependency Review는 PR 시점 의존성 게이트로 동작합니다. 정책은 SECURITY.md에 고정되어서, AI 변경도 동일한 승인 경계를 반드시 통과합니다."
  3. 확장 3 · 13:00~14:00 GHAS 5-layer 문서(`docs/ghas-setup.md`)를 열어 5중 방어선을 설명한다.
    "클릭: docs/ghas-setup.md. 확인: Code review -> CodeQL -> Secret scanning -> Enterprise controls -> Agent governance 순서를 따라가며 설명합니다. 멘트: 한 가지 도구가 모든 걸 막는 게 아니라, 다층 방어로 AI 변경 리스크를 낮춥니다."
  4. 확장 4 · 14:00~15:00 마지막에 `docs/preflight-checklist.md`로 Go/No-Go 기준을 보여준다.
    "클릭: docs/preflight-checklist.md. 확인: required checks, 보안, 운영 기준 항목을 함께 확인합니다. 멘트: 오늘 데모는 이벤트가 아니라 파일럿 승인 회의의 입력이며, 이 체크리스트를 통과해야 확산합니다."

3) 25분 스크립트 (심화)

  1. 심화 1 · 15:00~16:00 15분 스크립트를 완료한다.
  2. 심화 2 · 16:00~19:00 DDD 코드(`src/domain`, `src/application`, `src/infrastructure`)를 열어 경계 분리를 설명한다.
    "클릭: domain -> application -> infrastructure 순서로 3개 파일을 연속 오픈. 확인: 정책 로직과 유스케이스 조합, 저장소 구현이 분리되어 있는지 봅니다. 멘트: AI가 코드를 제안해도 경계가 분리돼 있으면 리뷰와 테스트가 쉬워지고 회귀 위험이 줄어듭니다."
  3. 심화 3 · 19:00~22:00 tool exception 템플릿과 Govern 이슈를 연결해 예외 승인 체계를 시연한다.
    "클릭: tool-exception-request 템플릿 -> Govern 이슈. 확인: 승인자, 만료일, 로그 제출 계획, 종료 기준 필드를 확인합니다. 멘트: 비표준 도구는 금지/허용 이분법이 아니라 조건부 예외 승인으로 통제합니다."
  4. 심화 4 · 22:00~25:00 slo-monitor 이슈와 cost-governance 문서를 열어 운영/비용 루프를 설명한다.
    "클릭: slo-monitor 결과 이슈 -> docs/cost-governance.md. 확인: SLO breach와 cost-review 라벨, T0~T4 작업 등급, budget alert 70/90 기준을 확인합니다. 멘트: 비용은 금지가 아니라 라우팅과 승인으로 통제하며, 운영 지표와 함께 관리합니다."

4) 장애 대비 Fallback

  • Actions 지연: `docs/sdlc-stage-evidence-map.md` 먼저 제시하고, "실행 로그가 늦어도 증적 맵은 고정되어 있습니다"라고 설명
  • Security 권한 부족: `SECURITY.md` + `docs/ghas-setup.md`로 대체하고, "화면 권한과 무관하게 정책 기준은 동일"이라고 설명
  • PR 없음: `pull_request_template.md`와 `CODEOWNERS` 파일 직접 오픈 후, "리뷰 경계는 템플릿과 오너 규칙으로 강제"라고 설명
